Customer Churn Platform — Interview Guide

Everything you need to explain your project clearly, simply, and with complete confidence.

Cheat Sheet & Quick Review

1. 🎤 How to Introduce Your Project (Say this out loud)

When the interviewer says: "Tell me about your project", use this simple 30-second answer:

"I built an end-to-end Customer Churn Prediction platform. In business, customer churn means when customers cancel their subscriptions or leave. My system uses Machine Learning to predict whether a telecom customer is likely to stay or leave, giving an exact probability score.

I also built a full web application using Flask where team members can enter customer details, see instant risk scores, view an analytics dashboard of churn rates, search past history, and export data to CSV. The app is live and deployed on Render."

2. 🗺️ The Project in 5 Easy Steps

1 Data Collection & EDA: We used real telecom customer data (7,000+ customers). During data exploration, we found that ~27% of customers churned. Customers on month-to-month contracts and high monthly charges left the most.

2 Data Preprocessing: Real customer data has both text (Contract, Payment Method) and numbers (Tenure, Charges). We converted text into numbers using One-Hot Encoding and scaled big numbers using StandardScaler.

3 Model Training: We trained a Logistic Regression model. It learns patterns and calculates probability: e.g., 85% chance to stay, 15% chance to churn.

4 Web Application: We built an intuitive user interface with Flask. It includes an input form, an Admin Dashboard showing churn trends, and a paginated history table with full edit/delete options.

5 Storage & Deployment: Every prediction is saved in an SQLite database. The application is hosted online using Gunicorn on the Render cloud platform.

3. 🛠️ Technology Choices: Why & How (In Simple Words)

Technology Why I Used It (Plain English) How I Used It in Code
Python The number one language for data science and web backend. It lets us connect machine learning directly to web pages easily. Used for everything: data cleaning, ML model training, database access, and the Flask backend.
Scikit-Learn The standard library for classical machine learning. It gives reliable tools to clean data and train models cleanly without bugs. Used ColumnTransformer to combine StandardScaler (for numbers) and OneHotEncoder (for text features).
Logistic Regression It is fast, simple, and provides true probability percentages (e.g. 74% risk), not just a flat Yes/No. Also easy to explain to business managers. Trained with LogisticRegression(max_iter=1000) in src/train.py and saved using Joblib.
Flask A lightweight web framework. Unlike Django which is heavy with lots of extra files, Flask is fast, flexible, and perfect for ML apps. Created web routes like /predict, /dashboard, and /history in app/backend/app.py.
SQLite A zero-setup database stored in a single file (churn.db). Great for prototypes and single-server apps without running a database server. Stored prediction records and admin accounts using SQL queries in database/crud.py.
Werkzeug Security Protects admin passwords. It turns plain text passwords like "admin123" into secure, irreversible cryptographic hashes. Used generate_password_hash when saving passwords and check_password_hash when logging in.
Joblib A fast tool to save Python objects and ML models into files so they can be loaded instantly in memory when the website starts. Saved model as churn_model.pkl and preprocessor as preprocessor.pkl.
Gunicorn & Render Gunicorn is a production server that handles multiple user visits at the same time. Render hosts the app on the internet. Configured in render.yaml with command gunicorn app.backend.app:app.

4. 🤖 Top Machine Learning Questions & Simple Answers

Q1: What is Customer Churn and why is it important for businesses?
Simple Answer: Customer churn means when a customer stops using a service or leaves a company. It is important because getting a new customer costs 5 to 7 times more money than keeping an existing one. If a company can predict who is going to leave, they can offer special discounts or better support to make them stay.
Q2: Why did you use Logistic Regression instead of Random Forest or Deep Learning?
Simple Answer: I chose Logistic Regression for three simple reasons:
  1. Explainability: It is easy to understand which factors matter most (e.g. high monthly fees or contract type).
  2. Probabilities: It outputs realistic probabilities (like "78% chance of churn"), which helps the support team prioritize who to call first.
  3. Speed: It gives answers in less than 2 milliseconds and uses very little memory on the web server.
💡 Analogy: You don't need a spaceship (Deep Learning) to cross the street when a bicycle or car (Logistic Regression) does the job faster and cheaper.
Q3: Why is "Accuracy" not the best metric for churn prediction?
Simple Answer: Because churn data is usually imbalanced. In our dataset, 73% of customers stayed and only 27% left.
If a lazy model simply guesses "Nobody leaves" every single time, it will be 73% accurate, but it is 100% useless because it failed to catch even one customer leaving!

That is why we focus on Recall (how many actual churners we caught) and ROC-AUC / Precision-Recall instead of just raw accuracy.
Q4: What is Data Leakage and how did you prevent it?
Simple Answer: Data leakage happens when the model accidentally "cheats" by seeing information during training that it wouldn't have in real life.

How I prevented it:
  • I split the dataset into Training (80%) and Testing (20%) first.
  • I fitted the scaler and encoder (fit_transform) only on the training data.
  • When processing the test data or live website input, I only used transform (never fit).
Q5: What are StandardScaler and One-Hot Encoding?
Simple Answer:
  • One-Hot Encoding: Machine learning models only understand numbers, not text. So for columns like Contract = "Month-to-month", it creates simple binary flags (1 or 0).
  • StandardScaler: It brings all numbers to a similar range. For example, TotalCharges can be $5,000, while Tenure is 12 months. StandardScaler puts them on the same scale so the bigger number doesn't unfairly overpower the smaller one.
💡 Analogy: Comparing kilograms and grams directly is confusing. StandardScaler converts everything into the same measuring unit.

5. 💻 Top Web & Backend Questions & Simple Answers

Q1: How does a prediction work from start to finish when a user clicks 'Predict'?
Simple Answer:
  1. The user fills out the form on index.html and submits it.
  2. Flask receives the data in the /predict route.
  3. The values are packed into a Python dictionary and sent to predict_customer().
  4. The saved preprocessor.pkl transforms the values into numerical features.
  5. The saved churn_model.pkl runs predict_proba() to get percentages for "Stay" and "Churn".
  6. The result is saved in the SQLite database and sent back to display on the webpage.
Q2: How did you secure the Admin section of the website?
Simple Answer:
  • Password Hashing: We never save plain passwords. We use werkzeug.security which turns passwords into encrypted hashes. Even if someone steals the database, they cannot read the passwords.
  • Custom Decorator: I built a @login_required decorator. If someone tries to view /dashboard or /history without logging in, it automatically redirects them to the /login page.
Q3: What is SQL Injection and how did you stop it?
Simple Answer: SQL injection is when a malicious user types SQL commands (like ' OR 1=1 --) into an input field to tamper with or steal database records.

How I stopped it: I used parameterized queries with question marks (?), like cursor.execute("SELECT * FROM predictions WHERE id = ?", (id,)). The database treats the input purely as plain text, never as executable code.
Q4: Why and how did you implement Pagination?
Simple Answer: If you have 50,000 customer records and try to load all of them at once, the webpage will freeze and crash the server.
I used SQL LIMIT 10 OFFSET ? so the database only fetches 10 records per page. This makes page loading super fast regardless of how many records exist.

6. 🚀 Future Improvements (What to say when asked: "What would you improve next?")

If the interviewer asks: "What would you do next to make this project even better?", mention these 4 realistic points:

1. Try XGBoost & LightGBM: "I would test advanced tree models (like XGBoost) against my Logistic Regression baseline to see if we can get a higher F1-score while keeping fast inference."

2. Add Explainability with SHAP: "I would integrate SHAP values into the user interface so for every customer, the screen explains why they are churning (e.g. 'Risk is 82% because of Month-to-Month contract and lack of Tech Support')."

3. Upgrade to PostgreSQL: "SQLite is great for development and small projects, but for a large enterprise company with many simultaneous users, I would migrate to PostgreSQL for high-traffic multi-user access."

4. Build a RESTful API: "I would create JSON API endpoints with Swagger/OpenAPI documentation so company tools like Salesforce or HubSpot can automatically check churn risk in the background."

5. Automatic Email / Slack Alerts: "If a customer's churn risk is greater than 75%, the system can automatically send an alert to the customer retention team to contact them immediately."
